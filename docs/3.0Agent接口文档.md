## 1. 真实产品流程

新版 Agent 项目不从项目中心选择普通项目。用户粘贴剧本或上传文件时，后端自动创建 `project_kind=agent` 的内部项目，并返回 `production_id`。

```text
创建 Agent 项目
  → 手动 start
  → 第一步：分集规划 + 资产及资产变体分析
  → 确认剧本处理结果
  → 第二步：管理资产、上传或生成资产图、确认资产
  → 后端按集并发生成分镜组
  → 第三步：编辑分镜组、绑定资产、按集或单分镜组生成视频
  ↘ 第四步：已完成分镜的集可并行进入审片、选片和交付
```

### 1.1 两种模式的真实差异

| 规则 | 审核模式 `supervised` | 自动模式 `automatic` |
| --- | --- | --- |
| 创建时视频模型 | 禁止提交 | 必须提交 |
| 创建时最低积分 | 不限制 | 余额必须至少 100 |
| 启动时最低积分 | 不限制 | 再次校验至少 100 |
| 文本模型 | 后端固定 `gpt-5.5` | 后端固定 `gpt-5.5` |
| 图像模型 | 后端固定 `gpt-image-2` | 后端固定 `gpt-image-2` |
| 补充剧本 | 支持 | 不支持，返回 `40982` |
| 视频模型/分辨率 | 第三步按请求选择，可按分镜保存配置 | 必须与创建时配置一致，否则返回 `40987` |
| 第一步确认 | 用户调用确认接口 | 当前代码仍要求调用确认接口 |
| 第二步确认 | 用户调用确认接口 | 当前代码仍要求调用确认接口 |
| 分镜分析 | 资产确认后按集并发提交 | 资产确认后按集并发提交 |
| 视频生成 | 按集或单分镜组提交 | 按集或单分镜组提交，不会自动提交整剧视频 |

因此，当前 `automatic` 表示“预先锁定视频配置并参与后台批量调度”，不是从上传到成片完全无人值守。前端必须保留第一步确认、第二步确认和第三步视频提交逻辑。

### 1.2 四步访问规则

以 `GET /agent-productions/{production_id}/workflow` 返回为准：

- `steps[].can_view=false` 时不得进入对应页面；强行调用受门禁保护的接口返回 `40990`。
- 第一步完成后才能查看第二步。
- 第二步确认并产生有效核心资产锁后才能查看第三步。
- 某集分镜分析完成后，该集即可进入第四步；不要求全剧分镜都完成。
- 第三步视频生成和第四步审片展示并行，第四步不会暂停第三步任务。

## 2. 通用协议

### 2.1 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "timestamp": "2026-08-21T10:00:00+08:00"
}
```

### 2.2 失败响应

```json
{
  "code": 40990,
  "message": "前置步骤尚未完成",
  "data": {
    "requested_step": 3,
    "required_step": 2,
    "current_step": 2,
    "required_status": "completed"
  },
  "timestamp": "2026-08-21T10:00:00+08:00"
}
```

错误响应可能携带 `X-Request-ID`。排查线上问题时应同时记录 HTTP 状态码、业务 `code` 和该请求 ID。

### 2.3 并发与幂等规则

- `expected_*_version`、`expected_revision`、`expected_lock_version` 必须来自最近一次查询响应。
- 版本冲突返回 HTTP `409`；刷新当前资源后重新编辑，不能盲目覆盖。
- `idempotency_key` 长度为 8～128 字符。同一次动作重试必须复用原值；新参数或新动作必须使用新值。
- 视频生成幂等键绑定请求签名；相同键配合不同参数返回 `40971`。
- 资产锁、剧本确认、视频生成、审片确认、交付和剪映导出都具有持久化幂等记录。
- 不要因为网络超时直接换幂等键。应先查询任务或资源状态。

### 2.4 通用枚举

`mode`：

```text
supervised | automatic
```

`generation_ratio`：

```text
21:9 | 16:9 | 4:3 | 1:1 | 3:4 | 9:16
```

`video_resolution`：

```text
360p | 480p | 540p | 720p | 768P | 1080p | 2K | 4k
```

`production.status`：

```text
draft | planning | waiting_approval | running | paused |
partially_failed | completed | cancelled
```

工作流步骤状态：

```text
not_started | processing | waiting_review | completed | failed | invalidated
```

## 3. 创建、配置和项目控制

### 3.1 粘贴剧本创建

```http
POST /api/v1/agent-productions/from-text
Content-Type: application/json
```

请求：

```json
{
  "name": "雨夜旧宅",
  "content": "完整剧本文本……",
  "style_id": "11111111-1111-1111-1111-111111111111",
  "generation_ratio": "9:16",
  "video_resolution": "1080p",
  "mode": "supervised",
  "video_model_id": null
}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `name` | 否 | 最长 128；文本 JSON 省略或 null 时取正文首个非空行，显式空白字符串返回 422；文件创建可回退文件名 |
| `content` | 是 | 去除首尾空白后不能为空；默认最多 100000 字符 |
| `style_id` | 是 | 必须是已启用风格 |
| `generation_ratio` | 是 | 使用通用比例枚举 |
| `video_resolution` | 是 | 使用通用分辨率枚举 |
| `mode` | 是 | `supervised` 或 `automatic` |
| `video_model_id` | 条件必填 | 自动模式必填；使用 `/api/v1/models/options?model_type=video` 返回的数据库 UUID `id`。审核模式必须为 `null` 或不提交 |

该 JSON Schema 为 `extra=forbid`，不得提交目标集数、单集时长、分镜时长、重试次数、试播数量、积分预算、文本模型或图像模型。

### 3.2 上传文件创建

```http
POST /api/v1/agent-productions/from-file
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `file` | 是 | `.txt`、`.md`、`.docx`、`.pdf` |
| `name` | 否 | 最长 128 |
| `style_id` | 是 | UUID |
| `generation_ratio` | 是 | 比例枚举 |
| `video_resolution` | 是 | 分辨率枚举 |
| `mode` | 是 | 模式枚举 |
| `video_model_id` | 条件必填 | 同文本创建；不是厂商 `model_id` |

默认文件限制：20MB、PDF 最多 500 页、文件名最多 255 字符、解析超时 30 秒。实际值可由服务端配置覆盖。

### 3.4 配置查询与修改

```http

PUT /api/v1/agent-productions/{production_id}/configuration
```

### 3.5 项目列表、详情和删除

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/agent-productions?status=&page=1&page_size=20` | 当前用户 Agent 项目分页列表；`page_size` 1～100 |
| GET | `/agent-productions/{production_id}` | 生产详情、内部步骤和确认点 |
| DELETE | `/agent-productions/{production_id}` | 软删除内部项目；未结束制作先执行 Agent 取消逻辑，具体任务处理范围见下 |
| GET | `/agent-productions/{production_id}/workbench` | 生产详情、矩阵、积分、控制器和可执行动作聚合 |

**删除时的 ID 来源：** 路径参数名为 `production_id`，但不同响应中的字段名如下，前端应在读取响应时明确映射：

| 来源 | 成功响应中的 ID 位置 |
| --- | --- |
| 创建 `/from-text`、`/from-file` | `data.production_id` |
| 列表 `GET /agent-productions` | `data.items[i].id` |
| 详情 `GET /agent-productions/{production_id}` | `data.id` |

从列表发起删除时，使用 `DELETE /api/v1/agent-productions/${item.id}`，不要读取列表项中不存在的 `item.production_id` 或内部 `project_id`。上表中的 `data` 是后端响应包络；前端请求工具如果已解包，应按实际返回层级取值。

发送前校验 ID 为合法 UUID；ID 缺失时禁止发送请求。删除进行中禁用该项按钮，避免重复请求。`/agent-productions/undefined` 会返回 HTTP 422 / `42200`，错误位置为 `path.production_id`，不会执行删除；这是请求参数错误，不应自动重试。成功后根据删除响应的 `data.production_id` 移除对应列表项。

列表只在 `should_poll=true` 时轮询，间隔使用 `next_poll_seconds`。当前默认返回 10 秒。

该值是 Agent 工作流列表的刷新间隔。资产图、分镜图和分镜视频的厂商结果等待统一由公共回收模块负责：首次立即入队，未完成时默认每 2 秒查询；生成 Worker 不再 sleep 等待。具体生成任务使用通用 task-records 单条/batch 查询时，活动任务 next_poll_seconds=1，终态为 null。单条/batch 增加 phase 字段，persisting 表示厂商完成后正在保存成品。也可使用通用 task-records/stream 合并订阅媒体任务状态，具体见 0.0 通用文档；工作流列表刷新契约不变。

DELETE 返回 AgentProductionDeletedOut：production_id、status、deleted。内部项目 is_enabled=false 后不可再访问；该内部字段不出现在删除响应中。Agent 取消仅处理活动步骤记录关联、状态仍为 pending 的任务，并对适用预扣退款；不会统一取消所有 running 任务，也不保证撤回已发送的供应商调用。它与普通项目 DELETE 的 pending/running 全项目处理范围不同。

### 3.6 开始、暂停、恢复和取消

```http
POST /api/v1/agent-productions/{production_id}/start
POST /api/v1/agent-productions/{production_id}/pause
POST /api/v1/agent-productions/{production_id}/resume
POST /api/v1/agent-productions/{production_id}/cancel
```

请求体均为空。

- `start`：校验配置、自动模式 100 积分门槛、固定文本/图像模型，然后提交第一步分析。
- 首次启动的分析步骤与待投递记录在同一事务中保存。队列暂不可用时仍返回 `planning`，由后台补偿投递；重复 `start` 不创建第二个步骤或第二条启动消息。
- `start` 对已经处于 `planning/running/waiting_approval/paused/partially_failed` 的任务为幂等无操作。
- 已完成任务不能再次 `start`，返回 HTTP `409`；补充审核模式剧本应使用补充接口。
- `pause`：停止派发后续任务；已经发送到厂商的任务仍可能完成。
- `resume`：仅允许 `paused` 或 `partially_failed`，按持久化步骤恢复。
- `cancel`：终止继续生产，保留已经生成的数据和积分记录；任务状态和退款范围见第 3.5 节。

第一步分析、剧本补充分析、资产/变体图片生成及异步交付使用持久化待投递记录。数据库提交后队列暂不可用时由后台补偿投递，不能把短暂 pending 判为失败，也不能直接重新创建制作或重复扣费。

## 4. 第一步：剧本处理

### 4.1 后端任务逻辑

新版工作流在前端表现为一步，后端严格使用两个模型任务：

1. `episode_planning`：模型根据剧情结构决定集数，并连续覆盖本次分析原文。
2. `asset_analysis`：基于分集结果提取人物、场景、道具及其剧情化变体。

本步骤不生成参考图，也不读取目标集数、单集时长或分镜时长。补充剧本仅分析新增原文范围，确认时合并到原有分集和资产，不重新提交整剧分析。

### 4.2 查询剧本处理结果

```http
GET /api/v1/agent-productions/{production_id}/script-package
```

响应按资产类型分组：

```json
{
  "production_id": "00000000-0000-0000-0000-000000000803",
  "script_version": 1,
  "bible_version": 1,
  "status": "waiting_review",
  "episodes": [],
  "characters": [],
  "character_variants": [],
  "scenes": [],
  "scene_variants": [],
  "props": [],
  "prop_variants": [],
  "warnings": []
}
```

基础资产包含 `id`、`asset_type`、`canonical_name`、`aliases`、`episode_numbers`、`confidence`、`merge_reason`、`review_status`、`content` 和 `lock_version`。

变体通过 `base_candidate_id` 关联主资产，并包含：

```text
variant_type | description | trigger_reason | episode_numbers |
source_evidence | content | review_status | lock_version
```

`source_evidence`：

```json
{
  "source_start": 120,
  "source_end": 146,
  "source_quote": "原文片段"
}
```


### 4.4 审核模式补充剧本

```http
POST /api/v1/agent-productions/{production_id}/script-supplements/from-text
POST /api/v1/agent-productions/{production_id}/script-supplements/from-file
```

文本请求：

```json
{
  "content": "追加剧本文本……"
}
```

文件接口只提交 multipart 字段 `file`。仅 `supervised` 支持；`automatic` 返回 `40982`。补充分析进行时，前端仍可查看并操作之前已经确认的资产和已完成分集。

### 4.5 确认剧本处理结果

```http
POST /api/v1/agent-productions/{production_id}/script-package/confirm
```

```json
{
  "expected_script_version": 1,
  "expected_bible_version": 1,
  "idempotency_key": "script-confirm-v1"
}
```

确认时校验：

- 分集连续覆盖本次原文范围。
- 没有未解决结构警告。
- 变体关联有效主资产。
- 变体具有合法类型、触发原因、关联集数和原文证据。
- 请求版本与最新版本一致。

成功后分集和基础资产写入内部 Agent 项目，第一步完成并进入 `core_assets`。

`reference_image=null` 表示清空。上传文件本身使用项目通用上传接口，Agent 接口只接收上传成功后的 URL。

#### 5.3.1 Seedance 图片审核与复用

Agent 视频现已复用通用上传审核缓存和 `/seedance2/private-avatar` 审核流程。它与核心资产 `review_status`、资产锁定、分集审片确认是独立状态。

上传本地图片时，调用 `POST /api/v1/uploads/file`，multipart 参数为 `file` 和 `purpose=seedance_reference`；保存响应中的 `image_id`、`url`、`review_status`、`can_reference`，再通过上述 PUT 接口绑定 `reference_image=url`。绑定接口本身不触发审核，也不接受新的 `image_id` 字段。

已有生成图片或已绑定的审核上传图片，使用以下入口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/agent-productions/{production_id}/core-assets/{asset_type}/{asset_id}/reference-image/review` | 登记或复用主资产当前参考图 |
| POST | `/agent-productions/{production_id}/core-assets/{asset_type}/{asset_id}/variants/{variant_id}/reference-image/review` | 登记或复用指定变体当前参考图 |

两个请求均无请求体，需要登录、拥有该制作且可访问工作流第二步；`asset_type` 为 `character/scene/prop`。不修改资产图片、资产版本或锁定状态。响应 `data` 使用通用 `SeedanceImageOut`：上传文件字段，加上 `image_id`、`review_status`、`can_reference`、`can_retry`、`retry_requires_confirmation`、`review_error`、`reused`。

- 当前用户、当前素材服务凭证范围内已登记的同一 URL，直接返回审核状态，不重新下载或提交审核。失败和待核对状态也原样返回，重试必须使用通用重试接口。
- 未登记的 URL 必须能匹配当前用户、当前项目、当前资产或变体的有效成功图片生成历史，包括 `result_urls` 中的候选图。后端读取图片、计算内容摘要，复用审核记录或创建一次异步审核；不重复上传 OSS。
- 同一用户在当前素材服务凭证范围内，内容相同但 URL 不同的图片复用审核记录。响应 `url` 可能是首次登记的地址；审核接口不会替换当前资产的参考图 URL，原地址通过内部映射参与校验。
- 没有参考图或缺少来源凭证返回 HTTP `400` / `40016`。历史手填 URL、普通上传但没有审核登记的图片，需要将原文件通过 `purpose=seedance_reference` 上传后重新绑定；仅拥有资产编辑权限不足以把任意 URL 登记为已验证图片。

后续统一使用：

```http
GET  /api/v1/uploads/images/{image_id}
POST /api/v1/uploads/images/{image_id}/retry-review
```

重试请求体、`uncertain` 的二次确认及凭证变更规则见 [通用接口文档](0.0通用接口文档.md)。同一图片在 Seedance 系列模型之间切换，且用户、素材服务凭证不变时，不重新审核。

前端在选用需要该审核的 APIMart Seedance 模型时检查所引用图片。当前不自动判断图片是否真人，人物、场景、道具及变体参考图均按相同规则登记；只有 `can_reference=true` 才能用于该类视频请求。其他模型不会被此审核门禁拦截，资产确认流程也不以它代替业务确认。

### 6.2 分镜组规则

- 分镜组按剧情顺序保存，一集中的 `group_number`/`shot_number` 连续排序。
- 单组剪辑估时 4～15 秒。
- 一个分镜组可包含多个镜头；单镜头结构包括景别、拍摄镜头、角度、运镜、画面、对白和资产绑定。
- 长对白应补充周围人物反应、动作或环境镜头。
- 提示词必须保留：固定画风、禁止字幕和文字叠加、纯画面、不要 BGM、不要配乐。
- 资产引用持久化为 `{{asset:binding_key}}`，前端可使用 `@` 选择器生成该 token。


- 至少修改一个字段。
- `storyboard_prompt` 与 `shots` 不能在同一次请求同时修改。

### 6.6 保存分镜组视频配置


### 6.7 按集生成视频

```http
POST /agent-productions/{production_id}/episodes/{chapter_id}/video-generations
```

```json
{
  "expected_core_asset_lock_version": 1,
  "expected_episode_revision": 3,
  "idempotency_key": "episode-video-v1",
  "video_model_id": "00000000-0000-0000-0000-000000000810",
  "video_resolution": "1080p"
}
```

按集接口会遍历本集分镜组：复用活动任务和已成功主视频，仅为可生成项创建任务。分镜组已保存的视频配置优先于本次默认模型和分辨率。

按集和单分镜组视频接口的新请求都检查生产状态：`paused` 返回 HTTP `409` / `40952`，`completed/cancelled` 返回 HTTP `409` / `40951`，核心资产处于 `core_asset_change_review` 返回 HTTP `409` / `40950`。拒绝发生在创建本次请求和扣费之前。

按集提交期间，每个新分镜任务提交前重新检查生产状态；如果此时暂停或取消，已提交项保留，后续未提交项通过 `items[].error_code/error_message` 返回原因。因此 HTTP `200` 不代表全部分镜提交成功，应检查 `submitted_count`、`failed_count` 和 `items`。同一幂等键、相同参数的已存在请求仍可重放查询原结果，不会重新派发；恢复后对未提交项使用新幂等键。

Agent 使用 Seedance 2.5 时，后端始终向厂商提交 `watermark=false`，分镜组视频配置不提供水印开关。

APIMart Seedance 视频请求默认携带 `nsfw_check=true`。内容或参考图被供应商拒绝时，任务返回脱敏失败原因。

```json
  "expected_core_asset_lock_version": 1,

  "scope_ids": ["00000000-0000-0000-0000-000000000815"],
  "idempotency_key": "retry-storyboard-v1",
  "confirm_over_retry_limit": false
}
```

跳过请求：

```json
{
  "expected_core_asset_lock_version": 1,
  "stage": "video",
  "scope_ids": ["00000000-0000-0000-0000-000000000816"],
  "reason": "已人工替换",
  "replacement_url": "https://oss.example.com/replacement.mp4",
  "idempotency_key": "skip-video-v1"
}
```

`stage` 为 `storyboard`、`image`、`video`。`replacement_url` 不能用于 `storyboard`，且一次只能替换一个媒体 scope。

当前新版四步流程的视频失败优先通过第三步按集或单分镜组生成接口重新提交，不要依赖旧批量视频重试。

积分规则：

- 自动模式 100 积分只做准入校验，不预扣、不冻结。
- 每个实际模型任务按所选模型的 `configuration.billing.policy` 逐笔扣费：文本按成功响应的 Token usage 结算，图片按数量和分辨率计费，视频按规范化时长、分辨率及参考媒体类型计费；空策略使用后端内置价格。
- 文本和视频模型的 `configuration.billing.base_points` 只表示使用模型所需最低账户余额；文本不预扣，视频按分镜组参数估算预扣。APIMart 成功返回 `credits_cost/cost` 时，真实人民币成本为 `credits_cost × 0.7`，真实成本积分为 `ceil(credits_cost × 7)`；文本和视频均按 `configuration.billing.multipliers.platform`（APIMart 默认 1.2）计算最终积分，图像继续按 `configuration.billing.base_points` 或图片策略扣费。
- APIMart 文本响应只含 `usage` 时，按模型 `apimart_credits` 策略中配置的“我们的价格” Credits 费率、Token 阶梯和平台率 1.2 结算，不使用官方价格。
- 实际费用高于预扣时按厂商结果完整补扣；因此余额可能形成欠额，补足至非负数前不能继续提交 Agent 或其他模型任务，返回业务码 `40003`。
- 每个模型任务创建时冻结计费快照，任务运行期间的管理端改价仅影响后续新任务。
- 提交失败或最终失败的任务按任务结算逻辑退款。
- `production.consumed_points` 是 Agent 聚合净消耗，详细账目以 `/costs` 为准。

## 9. 前端推荐调用顺序

### 9.1 审核模式

```text
POST /agent-productions/from-text 或 /from-file（mode=supervised）
  → POST /agent-productions/{id}/start
  → GET /workflow，按 should_poll/任务状态轮询
  → GET /script-package
  → 可选 PATCH /asset-variants/{variant_id}
  → POST /script-package/confirm
  → GET /core-assets
  → 可选上传/生成主图和变体图
  → GET /core-assets/readiness
  → POST /core-assets/confirm
  → GET /storyboards，逐集展示已完成结果
  → 编辑分镜和绑定资产
  → 选择视频模型、分辨率、时长
  → POST /episodes/{chapter_id}/video-generations
     或 POST /storyboards/{storyboard_id}/video-generations
  → GET /episodes/{chapter_id}/videos
  → 必要时 PUT /primary-video
  → GET /video-timeline
  → POST /episodes/{chapter_id}/approve
  → GET /delivery-readiness
  → POST /jianying-exports 或 /deliveries
```

审核模式可在第一步确认前或已有确认基线后追加剧本。追加分析时继续展示旧资产和已完成分集；新分集分析完成后重新确认最新 `script_version` 和 `bible_version`。

### 9.2 自动模式

```text
GET /points/balance（必须 >= 100）
  → GET /models/options?model_type=video
  → POST /agent-productions/from-text 或 /from-file
       mode=automatic，提前提交 video_model_id 和 video_resolution
  → POST /agent-productions/{id}/start
  → 后续步骤与审核模式相同
  → 所有 video-config/video-generations 请求继续携带创建时保存的
       video_model_id 和 video_resolution
```

后端会校验自动模式第三步视频参数不能偏离项目默认值。前端不应再次展示模型选择器，但仍需把配置值传入当前请求 Schema。

## 12. 上线对接检查表

- 只使用新版 `/agent-productions/from-text` 或 `/from-file` 创建入口。
- 保存 `production_id`，不依赖内部 `project_id`。
- 页面访问严格读取 `/workflow` 的 `can_view`。
- 只在 `should_poll=true` 时轮询，使用服务端建议间隔。
- 自动模式先检查 100 积分并选择视频模型；审核模式创建时不传视频模型。
- 所有编辑请求保存最新 revision/lock version。
- 所有可重试写操作保存并复用幂等键。
- 资产按人物、场景、道具分栏；变体始终挂在主资产下。
- 资产确认至少包含人物和场景，参考图可以为空。
- 生成变体图前确保主图存在。
- 分镜提示词的 `@` 选择结果持久化为稳定 asset token 和 binding。
- 自动模式视频请求使用项目保存的模型和分辨率，不能由前端替换。
- 多个成功视频版本时完成主视频选择后再进入审片确认。
- 剪映导出按 `platform` 区分 Windows 和 macOS，完成后再下载 `output_url`。
